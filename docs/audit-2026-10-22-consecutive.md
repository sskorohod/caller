# Аудит consecutive-переводчика

Дата: 2026-10-22. Код на момент аудита: `a4880cb`. Метод: 36 агентов, шесть областей,
каждая находка проверялась отдельным состязательным агентом с установкой «по умолчанию не подтверждается».

**Выжило 18 находок, отвергнуто 10.** Отвергнутые не перечислены, но одна стоит упоминания:
выброшенное возвращаемое значение `commit()` выглядело утечкой, однако `push()` отказывает
ровно на тех же двух условиях — буфер на сервере не растёт, и ограничение, которое якобы
обходилось, не обходится.

Исходное состояние: `tsc` чист, 269 тестов проходят, прод здоров. Аудит искал именно то,
чего эти гейты не видят.

Формулировки находок приведены **дословно**, как их дали проверяющие агенты, с номерами строк.
Я их не пересказывал намеренно: пересказ технического утверждения — это место, где теряется
точность. Порядок — по тому, что ударит по живому звонку раньше, а не по простоте правки.

## 1. A 4-second blip to api.openai.com permanently kills transcription mid-call; the line runs silent for 5 minutes and is then hung up

**ВЫСОКАЯ** · `services/consecutive/transcribe.ts`  ✅ исправлено (`0080e09`)

**Что ломается.** BACKOFF_S = [0.5, 1, 2] (transcribe.ts:35) is the entire recovery budget — three fast-failing connects consume it in ~3.5s — or three sessions each living under STABLE_S = 10 (what a realtime concurrency cap looks like). Either path sets alive = false permanently (transcribe.ts:293, 319); only start() ever sets it true, and the translator calls that once. From then on push() returns at transcribe.ts:137 WITHOUT even the rate-limited 'drops audio' warning, so the line vanishes with zero logging. The VAD keeps running, the floor gets no text, so no utterance opens, so no turn completes, so resetIdleTimer() is never called again and hangupOnIdle() ends the live call 5 minutes later. Two people on speakerphone talk into dead air and are then cut off. TranscriberLike (translator.ts:59-66) does not expose `alive`, so the translator cannot even see it, let alone restart the leg; and there is no mid-call fallback to the cascade (media-stream.ts:190 catches only a throw from start()). The surviving record is a session with duration ~300s, non-zero cost and metrics.utterances: 0, with no field anywhere saying the transcriber died.

**Правка.** Add an `onDead(reason)` option to TranscribeOptions and invoke it at the three sites that set alive = false (transcribe.ts:293, 300, 320) — NOT in aclose() (transcribe.ts:384), or every normal hang-up reports a dead transcriber. In the translator, handle it like onVadDead: write a durable call event (eventType 'transcriber_dead'), add it to summary() so translator_sessions.metrics carries it, and start a fresh TranscribeLeg with a bounded restart count (clearing this.commitDue, translator.ts:197, because a new session starts with an empty buffer). Do NOT implement this as 'tear the engine down so media-stream falls back' — detach() sets saved = true (translator.ts:843), so a teardown with no installed successor leaves the session never finalized, never billed, never 'completed'. Bind callId into the leg's logger while here: transcribe.ts:19 is module-level, so none of its error lines can be attributed to a call when several run at once.

**Вместе с.** Fix #6 (call-start timeout budget) in the same commit — both edit the same connect/backoff constants and pull in opposite directions. See the conflicts field.

## 2. A deliberate /pause hangs up the customer's live call five minutes later

**ВЫСОКАЯ** · `services/consecutive/translator.ts`  ✅ исправлено (`7facfd5`)

**Что ломается.** pause() (translator.ts:763-768) and resume() (770-773) touch no timer. resetIdleTimer is called from exactly three places — startTimers (371), settleText (612), onFinished (618) — and while paused sendAudio returns at 416 and onVad at 427, so no utterance can be created and neither re-arm site is reachable. The deadline armed before the pause therefore stands, and hangupOnIdle (392-410) has no paused guard: it looks up the Twilio SID and really ends the call (telephony.service.ts:178-181), then finalizes. resume() re-arms nothing, so a short pause taken late in the window drops the call seconds after resume. This is a shipped, advertised control with two live callers: /pause in Telegram (telegram-commands.service.ts:149, in HELP_TEXT) and the Pause button on the public share-token page (translate/[token]/page.tsx:419-427 -> socket-server.ts:224).

**Правка.** In pause(), RE-ARM rather than clear — a pause-specific window (PAUSED_IDLE_TIMEOUT_MS, 15-20 min). Do NOT simply clearTimeout: the 5-minute idle timer is the money guard, and account() (translator.ts:909-917) bills wall-clock seconds that keep running while paused, so a cleared timer leaves only the 4-hour safety timer and a user who taps Pause and walks away is billed up to 4 hours at $0.20/min. In resume(), call this.resetIdleTimer() so the normal five minutes restart from the resume. Keep resetIdleTimer's `if (!this.persist || this.closed) return` guard or tests and the smoke scene start arming real timers. Also call resetIdleTimer() from the 'stop' case (translator.ts:518-522) so an interrupted-but-real turn counts as activity. Apply the identical change to stealth-translator.ts:885-886 or the VOICE_ENGINE=pipeline rollback keeps the defect.

## 3. After a pause or restart the interpreter hears its own voice as a new speaker and reads the caller's own sentence back to them

**ВЫСОКАЯ** · `services/consecutive/floor.ts`  ✅ исправлено (`58f4593`)

**Что ломается.** pause() (floor.ts:778-786) and restart() (793-805) are the only two ways playback stops that do NOT set finishedAt — finished() (333), interrupt() (738) and pauseAll() (393) all do — and restart() additionally erases playing.translation. playedTexts() (961-966) admits only `state === 'playing'` or `finishedAt !== null`, so the just-played text drops out of the echo memory exactly when listening() is still open for ECHO_TAIL_S = 1.5s, i.e. exactly when the tail of that audio returns off the room mic. Reproduced: after pause(#1), our own echoed ' the technician will come tomorrow morning' opens candidate #3 (en), the intent judge is asked with playing = "" (floor.ts:512, this.playing is now null) so the model cannot recognise its own echo either, answers 'later', and #3 is released — queued to be translated back into Russian and spoken at the man who just spoke. Identical after restart(). Stop-word flavour: our own echoed ' Wait' scores counts.stop_phrase: 1. Control with #1 still 'playing': no candidate at all, so the delta is entirely the lost memory. Each occurrence writes a phantom turn into the saved transcript and burns an intent call, a translation and a TTS. The trigger (speaker continuing over the translation of their own words) is a common path the code comments attribute to repeated live calls.

**Правка.** Add `lastSoundedAt: number | null` to Utterance, set it ONLY where sound actually reached the line — finished/interrupt/pause/restart/pauseAll, never textDone() (377-384, whose comment deliberately withholds finishedAt because a text-only reply never sounded) and never drop(). Change playedTexts() to `u.state === 'playing' || (u.lastSoundedAt !== null && now - u.lastSoundedAt < ECHO_MEMORY_S)`. In restart(), push the discarded translation onto a FloorManager-level ring of [text, now] pairs BEFORE clearing it, pruned on write and capped (a handful of entries at ECHO_MEMORY_S = 10s), and have playedTexts() concatenate it — the engine re-translates, so the old wording is otherwise unrecoverable (floor.translation() has one caller, translator.ts:583, and translator.ts:505-514 deletes this.translations on restart too). ALSO move sourceOfPlayback() (955-959) onto lastSoundedAt: it keys off finishedAt as well, and after a pause it returns a stale utterance that feeds `echoPossible` at floor.ts:464 — if that stale source carries the incoming echo's lang, echoPossible goes false and the echo is not filtered at all, defeating the rest of the fix. Pass the pre-empted text as the intent request's `playing` at floor.ts:512. New test must feed echo INTERLEAVED into the continuation after pause() and after restart(); floor.test.ts:382 keeps #1 playing and will not catch a regression.

**Вместе с.** Land this BEFORE #13 (playback lead), which shifts playedUntil/finishedAt by +400ms and moves the window this predicate measures against.

## 4. A refused session on a reconnect is logged and ignored: the leg reports healthy and appends into a session that will never transcribe

**СРЕДНЯЯ** · `services/consecutive/transcribe.ts`

**Что ломается.** On a reconnect, open() is called with awaitAccept = false, so `up()` runs at transcribe.ts:252-253 the moment session.update is written to the socket, before any answer. The server's refusal then lands in handle() (358-366) and only log.warns, while `connected` stayed true and `alive` was already true — so push() and commit() keep running into a session the server never configured. The first session treats the identical event as fatal (267-272, fail('session refused')); the reconnect does not. Reproduced with a fake socket answering {type:'error', code:'rate_limit_exceeded'} and staying open: alive = true, socket open, 15000 appends accepted, 299 commits sent, audioSeconds 300.0. Not one delta comes back, the floor gets no text, no turn completes, and the idle timer ends the call ~5 minutes later. The retry machinery is bypassed entirely: a transient refusal that two more attempts would have survived is recorded as success and never retried.

**Правка.** Keep `up()` immediate (not blocking on the answer is correct) but stop IGNORING the answer: record an `accepted` flag per socket, set on 'session.updated', and call this.lost(ws) for a SESSION-LEVEL error on a socket that is not yet accepted, so the backoff applies and the leg can give up visibly. Two guards the naive version needs: exempt COMMIT_EMPTY, and gate commit() (not push()) on `accepted` — on a reconnect audio and commits flow immediately (transcribe.test.ts:765-767 asserts that) and minCommitBytes is only 800 bytes for pcmu (100ms), so a commit can reach the server inside the acceptance RTT and its answer would otherwise be read as a refusal and tear down a healthy socket; since `began` was just set, lost() counts it short, and three such seams kill a good leg. Act only on an error whose shape names the session (e.g. invalid_request_error with `param` under `session.`). Surface the refusal count in translator_sessions.metrics while here — today a refused session is indistinguishable from a healthy silent call.

**Вместе с.** Same file and same lifecycle as #1 and #6; do all three transcribe.ts changes in one commit so the accept/backoff semantics are decided once.

## 5. The only durable record of a cascade fallback carries a constant string; four distinct causes collapse into 'transcriber did not start'

**СРЕДНЯЯ** · `services/consecutive/transcribe.ts`

**Что ломается.** TranscribeLeg.start() (transcribe.ts:123-130) returns a bare `false` for all four of: a synchronous connect throw with code/HTTP status (211), a handshake/close failure with closeCode (237), the accept timeout (260), and an outright session refusal with the server's error.code/type (270-271) — each reported only into pino. translator.ts:304 turns that into `new Error('transcriber did not start')`, and media-stream.ts:210 stores exactly that message as the `translator_fallback` reason. The sibling branch at translator.ts:307 is dead code (CascadeEngine.start() is `return true`, engine.ts:270-272), and every other boot failure already carries a real message — so the transcriber, the likeliest failure and the one depending on the network and the admin key's model access, is the only anonymised one. Those four causes need four different fixes (config / infra / network / quota) and the record cannot tell them apart, which is why the 09-29 pair is unrecoverable.

**Правка.** Add `lastFailure` to the leg, set from the fields it already logs, in BOTH the fail() closure (transcribe.ts:225, under the existing `if (ws === this.ws)` guard) and the synchronous connect catch at 210 which bypasses fail(). Shape it structurally — { kind: 'connect'|'handshake'|'refused'|'not_accepted', code?, type?, status?, closeCode?, timeoutMs? } — so the reason stays queryable by code, not by substring. Declare it OPTIONAL on TranscriberLike (translator.ts:59-66) or `tsc --noEmit` breaks on the test fakes and the smoke-scene transcriberFactory, which today exits 0. Attach it at translator.ts:304 as the Error's `cause` and spread it into eventData in media-stream.ts; translator.test.ts:616 matches /transcriber did not start/ as a substring so it keeps passing. Carry only why()-safe fields, NEVER err.message — transcribe.test.ts:719-726 asserts the message stays out of the log because it can carry the key, and this now lands in durable storage. Skip the symmetrical change at translator.ts:307. PREREQUISITE: deploy b3e2e74 — prod is a4880cb and the fallback event itself is not live yet.

**Вместе с.** This IS the answer to the live question; ship it with the b3e2e74 deploy. Its lastFailure plumbing is also what #1's onDead reason should carry.

## 6. Call start can burn two serial 10-second budgets before falling back, and the caller is neither heard nor spoken to for all of it

**СРЕДНЯЯ** · `services/consecutive/transcribe.ts`

**Что ломается.** The two timeouts are consecutive, not alternative: `handshakeTimeout: HANDSHAKE_TIMEOUT_MS` is baked into the default connect factory (transcribe.ts:112-113) and governs TCP/TLS/upgrade, and only once `ws.on('open')` fires does the accept timer get its own full acceptTimeoutMs, defaulted to the same 10s (116, 258-261). A slow-but-successful upgrade followed by a session.update the server never answers costs ~20s; the ordinary single-failure case is 10s. `await Promise.all([loadSilero(), transcriber.start()])` (translator.ts:299) has no deadline, nor does startTranslator or the media-stream `start` handler that awaits it. For the whole of it the caller is on a live PSTN call hearing nothing: the inbound TwiML is a bare <Connect><Stream> with no <Say> and no hold music (twilio.ts:227-236), the greeting is scheduled only after boot() completes (translator.ts:317) and then waits its own greetingDelaySeconds, and inbound media frames are discarded because __conferenceTranslator is assigned only at media-stream.ts:824, after the await. The author's own comment at transcribe.ts:38 budgets ONE such wait for call start; line 116 silently adds a second.

**Правка.** Add an outer race in boot() around the Promise.all (a rejection is caught by start() -> close(), which allSettles transcriber.aclose() and cuts a socket still coming up, so nothing leaks and media-stream falls back as it already does). That alone gets the whole benefit at no risk. If a tighter leg budget is also wanted, scope it to the first session ONLY — a per-attempt handshakeTimeoutMs passed from open(true) — and do NOT shorten the shared closure, because reconnect() uses it and three 1.5s attempts on this host's intermittently filtering resolver would exhaust BACKOFF_S and leave a live, billing call with no text and no cascade to fall back to. Drop the finding's claim that this explains the 09-29 pair: those two calls each completed a translated turn inside 13-14s, which fits a millisecond-fast refusal far better than a 10s burn.

**Вместе с.** Must be designed with #1 — see the conflicts field: HANDSHAKE_TIMEOUT_MS and BACKOFF_S.length are each doing two jobs.

## 7. Two in-range settings values invert the release gate: backchannels and transcription garbage get spoken aloud into the room

**СРЕДНЯЯ** · `services/consecutive/settings.ts`

**Что ломается.** end_silence_ms accepts 300..3000 and hard_end_ms accepts 800..8000 (settings.ts:23-24), the ranges overlap, and nothing — not the schema, not parseConsecutiveSettings (which only applies `??` defaults), not the admin UI's per-field check (admin/settings/page.tsx:218) — requires hard_end > end_silence. floor.ts then orders its rules by silence elapsed with hardEndS as the intended last gate (627, 630, 637, 649, 660). One natural single edit inverts it: raise 'End-of-thought pause' to 3000, its advertised maximum printed in the UI hint, and leave 'Hard limit' at its 2200 default — save() always sends all five fields. Reproduced on the real FloorManager: defaults drop [[2,'backchannel']] and release [1]; inverted drops [] and releases [1,2] with utt 2 = 'uh-huh' reason 'hard'. So a Russian 'uh-huh' said in the English speaker's pause is translated and SPOKEN, and the same bypass hits the 'overlap' drop, so mis-transcription garbage ('uda moica') is spoken too. The semantic and punctuation paths also go dead — every utterance releases at hardEndS, cutting unfinished thoughts EARLIER than the default — while every gpt-4.1-mini judge call is still issued and billed on a verdict that can no longer be acted on.

**Правка.** Both halves are load-bearing. (a) Add a cross-field refine to consecutiveSettingsSchema requiring hard_end_ms > end_silence_ms when both are present. (b) Because the schema is .partial(), a direct API PUT of one field alone still skips the refine — so ALSO repair in parseConsecutiveSettings: `hardEndMs = Math.max(hardEndMs, endSilenceMs + 100)`. That is range-safe (worst case 3100, under the 8000 max) and a no-op on every valid pair, so the three existing settings.test.ts assertions keep passing. Verified: with both applied, tsc exits 0 and the suite stays 269/269. Mirror the check in the admin UI's save() for the error message. Benign side effect: translator.ts:808 writes the settings into metrics, which will now record the repaired value — i.e. what actually ran.

**Вместе с.** Verify in one pass with #7 — both change the release gate, and #8's clamp restores the very gate #7's unsure verdicts fall through to.

## 9. An unsure judge answer is treated worse than no answer: +1.5s of dead air on exactly the short clear utterances the fast path exists for

**СРЕДНЯЯ** · `services/consecutive/floor.ts`

**Что ломается.** floor.ts:292 stores `confidence >= threshold ? complete : null`. A stored null matches none of true / 'failed' / 'ask' at floor.ts:645-658, so neither the semantic nor the punctuation path can fire and the text is never re-asked (decideReleases only re-asks when !verdicts.has(text)). Measured on 'I spoke with the customer yesterday.' (6 words, final period), end of speech to release: no answer -> 0.75s punctuation; judge errored/timed out -> 0.75s punctuation; complete/0.95 -> 0.75s semantic; complete/0.79 -> 2.25s hard; incomplete/0.70 -> 2.25s hard. A weak answer is strictly worse than no answer — a monotonicity violation — roughly doubling latency against the project's own ~1.2-1.3s p50 baseline. And the knob inverts: semantic_threshold is operator-tunable to 0.99 (settings.ts:27), at which EVERY judge answer stores null and both fast paths are dead engine-wide, so an admin tuning for 'safer' gets uniformly worse latency. Metrics show only release_hard while the event log says 'judge #N complete 0.70', so the two never line up — an unsure answer increments no counter at all.

**Правка.** At floor.ts:292, fall back to 'failed' — the same path as no answer, which is what the null branch's own comment says should happen — and add this.inc('judge_unsure') so the two stay distinguishable in metrics. Verified: applied, tsc exits 0 and the suite stays 269/269, and the probe returns 0.75s punctuation for unsure cases while a CONFIDENT incomplete/0.95 still correctly waits to 2.25s. ONE CAVEAT the finding omits: this also releases an unsure-INCOMPLETE phrase at 0.75s, discarding the model's weak lean toward 'not finished'. Defensible (it only fires when the text already ends in a sentence mark and is <= FAST_WORDS, which is exactly the no-information default, and route()/lateOwner() appends a continuation to the released utterance and emits 'updated'), but the strictly safer variant is to fall back to 'failed' only when the sub-threshold verdict is `complete` and keep waiting on a sub-threshold `incomplete`. Ship that variant.

**Вместе с.** Verify in one pass with #8 — the hard_end/end_silence clamp restores the gate these verdicts fall through to.

## 10. A translation unit lost to a transient API error is never retried and leaves no per-turn trace, while the record shows the turn as fully translated

**СРЕДНЯЯ** · `services/consecutive/engine.ts`

**Что ломается.** send() marks the source as sent BEFORE the call runs (engine.ts:461, `u.sent = u.text.slice(0, end)`), and the catch at 617-621 counts usage.errors, log.warns and returns — with maxRetries: 0 deliberate at 807-809 and no engine-level retry anywhere, so the unit is gone. Multi-unit utterances are the normal case, not an edge: settle() sends each stable sentence end as its own unit while the person keeps talking. The project's own test asserts this as intended (engine.test.ts:581 drives three units, fails the middle one, asserts audio == [Раз.]+[Три.]). The caller hears sentence 1 and sentence 3 with the middle one missing. Then logTurn writes `translated` from the translations map, which onText already filled with units 1 and 3, so it is non-empty, turn.untranslated is NOT set, and the transcript, the /translate page and the Telegram report all show a normal complete-looking turn. EngineCallbacks (89-93) is only onAudio/onText/onDone — there is no channel back to report the loss. The only durable trace is engine_usage.errors, a bare aggregate that is incremented from BOTH the text unit (618) and a TTS phrase (715), so it cannot even distinguish a lost sentence from a lost voicing; the pino logger is unbound (26) so the warn carries no callId. CLAUDE.md's silent-drop SQL on `untranslated` returns nothing for this entire class.

**Правка.** Do the reporting half fully, the retry half narrowly. (1) Add onSkipped(utt, sourceText) to EngineCallbacks and call it from the catch; record it on the turn as a NEW optional field (turn.partial with the dropped source, added to the Turn interface at translator.ts:135) — NOT turn.untranslated, which means 'nothing was translated' and drives the admin health alarm. Additive JSONB, so the transcript shape and the emitTurn socket payload (deliberately byte-identical to StealthTranslator's) are undisturbed. (2) Retry ONLY when said.length === 0, i.e. the call failed before the first delta — which is where a 429 or a connection reset lands. Once any delta has arrived, say() has grown u.said, called onText (feeding the echo filter and the transcript) and handed phrases to TTS, so a re-issue duplicates text into the echo filter and audio into the room; and 'retry only the un-streamed remainder' is not implementable. Cap the retry well under a second: HEAD_TIMEOUT_S = 10 (floor.ts:41) means a slow retry on the FIRST unit can land after the floor has moved on, turning one lost sentence into a lost turn. No naive 'retry once immediately' into a saturated shared admin key.

**Вместе с.** Design the transcript fields with #10 in one sitting — see the conflicts field; `untranslated` must keep exactly one meaning.

## 11. Released utterances dropped as 'interrupted' or 'overlap' never reach the call transcript

**СРЕДНЯЯ** · `services/consecutive/translator.ts`

**Что ломается.** The drop case (translator.ts:523-530) logs only a four-item whitelist: 'no translation' via logTurn, and 'backchannel' / 'ack' / 'stale' via logSkipped. floor.ts emits ten other reasons, and three carry a complete utterance that reaches neither: 'interrupted' (floor.ts:747, a released sibling killed by a barge-in), 'no audio' (689, a released head that waited HEAD_TIMEOUT_S with no sound), and pauseAll's reason (399). A 'released' utterance has already passed MIN_LETTERS and a release decision, so it is a whole thought. Reproduced on the real translator for crosstalk A(ru) -> B(en) -> A(ru) then a stop-word: #1 ru playing, #3 ru released with reason 'punctuation' and its translation present in the map; B's interrupt() produced drop commands `#2 overlap` and `#3 interrupted`, and the transcript ended with ONE turn out of three real utterances — #2 being a full sentence from the other speaker. Nothing rescues them: shutdown (866-869) logs only playing/open/released/candidate, never 'dropped'. The user- and admin-visible transcript (admin/sessions/page.tsx:79-100) shows a conversation in which the caller never said it, and the team already fixed the two sibling cases on exactly this principle (test comments at translator.test.ts:664, 676-678: 'what was said must stay').

**Правка.** Invert the whitelist — log by default, name only the reasons whose text is genuinely not lost: `const MERGED = new Set(['merged','echo','short','empty','lead_in','overlap'])`, then `if (reason === 'no translation') logTurn(utt, false); else if (!MERGED.has(reason)) logSkipped(utt, reason);`. logSkipped already guards greetings, empty text and double-logging. TWO AMENDMENTS to the obvious version: 'overlap' must be EXCLUDED (floor.ts:625-634 drops it deliberately for transcription garbage under 6 words heard inside the other side's speech — its own comment cites 'Мастер из' as 'Master is'; nothing reads the `skipped` field and admin/sessions renders every entry, so logging it would print mis-transcription scraps as turns). And 'no audio' must stay on logSkipped, NOT logTurn: logTurn sets untranslated only when the translation map is empty, so a 'no audio' drop would assert a translation the caller never heard, unmarked — and `untranslated` drives the admin health alarm (routes/admin/index.ts:221-230). Verified: the inverted whitelist applied cleanly with tsc 0 and 269/269, so nothing depends on the omission.

**Вместе с.** #11 — same transcript fields, and the two must agree on what `untranslated` means.

## 12. PhraseChunker counts words with /\S+/, so Chinese and Japanese translations are never cut: the streaming-TTS head start is dead for zh/ja

**СРЕДНЯЯ** · `services/consecutive/engine.ts`

**Что ломается.** TOKEN = /\S+/g (engine.ts:71) matches a space-free CJK run as ONE token; the buffer never ends in whitespace, so `ends.pop()` at 134 empties the list and cut() returns null forever. Measured on the real exported PhraseChunker streaming 4 chars at a time: a 42-char Chinese sentence yields [] during streaming and the whole sentence at flush, a 59-char Japanese one the same, while the equivalent English yields 2 phrases during streaming. This also makes the CJK sentence marks that ARE in PHRASE_MARKS (。？！ via SENTENCE_END, policy.ts:13) unreachable — the token count breaks first, so the missing CJK commas (，、；：) are a second-order problem. zh/ja are user-selectable and marketed, and isCrossScriptPair returns true for en/zh, ru/zh, en/ja, so these calls DO route to the consecutive engine. Consequences: the whole unit must finish streaming before any TTS starts, and — the strongest part — synthesizePhrase logs and returns on error (713-717), so one TTS failure or 15s timeout drops the WHOLE sentence for zh/ja where it would drop one phrase for en, inverting the engine's own 'a scrap of the last one is worse than silence' trade-off. Zero production exposure so far (all 6 calls were ru-en or pt-en), which is why this sits below the ru-en items.

**Правка.** Give cut() its own CJK-aware token regex — do NOT change TOKEN, realign() (865) depends on its whitespace semantics: match one ideograph/kana per token with the CJK branch first and one run per non-CJK stretch, and pop the trailing token only when it is a non-CJK run and the buffer does not end in a space (a CJK token is already complete). Add ，、；： (U+FF0C, U+3001, U+FF1B, U+FF1A) and the Arabic comma ، (U+060C) to PHRASE_MARKS — Arabic is space-separated, so that one is a free independent win. CRITICAL AMENDMENT, verified by implementing the naive version: the maxWords forced cut then splits Chinese WORDS mid-word, because one CJK token is one character, so maxWords = 20 falls inside a normal sentence — it produced '...检查冰' | '箱的压缩机问题', splitting 冰箱 (refrigerator) across two TTS requests, which the model reads as two unrelated syllables. So either scale the thresholds per script (CJK needs ~3-5x the token counts for the intended ~40-100 char phrase) or refuse the forced cut when the boundary would fall between two CJK characters and let the unit flush whole, keeping only the mark-based cut. Then add the test: a long Chinese sentence yields >= 2 phrases during streaming AND no boundary falls inside a multi-character word in the unpunctuated case.

## 13. A barge-in just after a pause in our own audio silently drops up to 140 ms off the end of the previous phrase

**НИЗКАЯ** · `services/consecutive/playback.ts`

**Что ломается.** remember() trims the phrase memory to LEAD_FRAMES = 5 on the first voiced frame after a GAP_FRAMES silence (playback.ts:196), and it runs BEFORE the write (154) — while TwilioOut still holds 19-20 unplayed frames, all of which clear() discards. pause() then restores only what is left in this.phrase (101-111). Reproduced with the real Playback + real TwilioOut and a FIFO playout model: frames of phrase A never heard in either pass = max(0, 20 - g - k), i.e. 140 ms at a 240 ms seam with a barge-in 1 frame into phrase B, 80 ms at a 300 ms seam, zero once the seam is >= 380 ms. The listener's heard position is ~400 ms behind the writer, so they hear A truncated ('...I'll be there on Thursd') and the resume jumps to B — permanent loss of translated speech, and precisely the fragment the pause mechanism was written to prevent. Narrower than first reported: the window is 20-140 ms wide and needs the seam silence in the 240-380 ms band, and a barge-in within RESTART_S = 3s produces restart() (whole translation redone) rather than this path.

**Правка.** Do NOT use the obvious `slice(-Math.max(LEAD_FRAMES, QUEUE_MS / FRAME_MS))` — I applied it and playback.test.ts:206 fails, because the kept 20-frame window BEGINS with voiced frames (the tail of A), so the resume replays already-heard audio; it also hard-codes a Twilio transport constant into a module that only knows the PlaybackOut interface. Correct shape: add leadMs() (or unheardFrames()) to PlaybackOut, implemented by TwilioOut from its own aheadUntil, and keep a small ring of the last ~20 written frames independent of the phrase memory. pause() then rebuilds as [frames still unheard per leadMs()] + [LEAD_FRAMES silence] + [phrase from its start] + [rest of buffer] — chronologically ordered, loses nothing, and with a real lead of 0 (the test Sink) the unheard prefix is empty so playback.test.ts:206/208 keep passing unchanged.

**Вместе с.** #13 — both need the same new leadMs() on PlaybackOut; add the interface method once.

## 14. Playback reports an utterance finished 400 ms before it stops sounding, so a barge-in in that window truncates its tail at Twilio

**НИЗКАЯ** · `services/consecutive/playback.ts`

**Что ломается.** The buffer is empty as soon as the LAST frame has been handed to TwilioOut, which by construction still holds up to QUEUE_MS = 400 ms of it — so notify() (playback.ts:144-150) -> onFinished -> floor.finished() runs 400 ms before the listener stops hearing the reply. Reproduced with the real pair on a virtual clock: last frame handed over at 1600 ms, onFinished at 1600 ms, last frame stops sounding at 2000 ms. The originally-claimed echo-window consequence is BACKWARDS and should be dropped — playedUntil is set at the notify instant, so listening() stays TRUE through the residual sound and still leaves 1.1 s of margin. What survives: (a) in the echo-absent case (echo.ts correlation < 0.7 -> setEcho(false)), decidePlayback's `quiet` gate no longer holds the next utterance, so a back-to-back reply's playAt is stamped 400 ms before its first sound and metrics.latency_ms p50/p90 understate that turn by up to 400 ms; (b) more important, any safeClear() between notify and the real end — speaker goes on over his own translation -> pause/restart -> TwilioOut.clear() — drops Twilio's whole buffer, which still holds the previous utterance's last ~380 ms, while the transcript records it as done rather than interrupted.

**Правка.** Extend PlaybackOut with leadMs() and delay notify(utt) by the current lead before firing, letting the floor stamp playAt accordingly. Do NOT use Twilio marks: Twilio delivers no mark for audio dropped by `clear`, and this engine clears on every stop/pause/restart/discard, so a lost mark means onFinished never fires, this.playing stays non-null and decidePlayback returns at its first line for the rest of the call — there is no watchdog for a stuck `playing`. Marks would also put a Cloudflare-tunnelled round trip on the completion path. The delayed-notify version needs three guards the obvious patch omits: close() must still settle run() with a notify pending; a stop/pause/restart/discard during the delay must cancel it (generation check, not just `gone`); and the +400 ms shift of finishedAt/playedUntil/logTurn must be accepted and the floor echo-window and PROMOTE_S fixtures re-checked. If only the metric is wanted, the zero-risk version is to leave completion alone and subtract leadMs() when stamping playAt.

**Вместе с.** #12 (shared leadMs()) and ordered AFTER #3, whose echo predicate this shifts.

## 15. The event timeline stops ~5 minutes into every call, so a 4-hour call's metrics hold nothing after its first ~55 turns

**НИЗКАЯ** · `services/consecutive/floor.ts`

**Что ломается.** log() silently drops everything past EVENTS_MAX = 300 (floor.ts:71, 968-972) — no else, no counter, no marker — and the array leaves the module only at translator.ts:818, inside the metrics written once at finalize. Reproduced on the real FloorManager over 4 hours of alternating ru/en turns: the cap fills at turn 55, t+312s, last stored event t+308s of 14402s, ~98% of the timeline absent; with barge-in traffic (8.1 events/turn) the cap fills at turn 37, t+153s. No test comes near it — instrumenting log() across the whole consecutive suite shows a peak of 36 events held by any FloorManager. The loss is narrower than first claimed and purely diagnostic: `this.transcript` (translator.ts:625-657) and the `consecutive_turn` log line are both uncapped and per-turn with timestamps, so ordered 'what happened when' survives minute 40 fine. What is actually lost past ~5 min is the sub-turn micro-sequence — judge verdicts with confidence, intent verdicts, echo on/off flips, candidate/prepare/merge/pause/restart ordering with ms timing. Also drop the tie to the 09-29 fallbacks: those stored no metrics at all, and the cap preserves exactly the call opening a start-time question needs.

**Правка.** Make it a hybrid ring, not a tail ring: reserve a head window (first ~100 entries) for the call opening — which is the one window the field has actually needed — and roll the remainder, with this.inc('events_dropped') so the truncation is explicit. A plain shift()-only ring is a net regression, since metrics are written once at finalize and it would discard the start of every call. Raise the cap while there: measured, an entry is ~39 JSON bytes, so 300 is ~11.4 KB (not the ~2 KB claimed) and an uncapped 4-hour call would be ~1 MB — ~2000 entries (~78 KB) is the defensible bound. `readonly` binds the reference only, so shift() is legal.

## 16. A mid-call engine swap discards the detached engine's metered provider spend, and a successor that fails to start loses the whole call's billing

**НИЗКАЯ** · `services/consecutive/translator.ts`

**Что ломается.** detach() sets saved = true (translator.ts:843), which makes finalize() a no-op at 898, so account() — the only place costParts() is charged — never runs for that engine, and TranslatorCarryover (models/types.ts:417-422) carries no cost field. The successor then bills from the inherited startTime. Reachable by an ordinary user twice over from the public share-token page: the stealth button (translate/[token]/page.tsx:409 -> socket-server.ts:183-191 -> media-stream.ts:250) and a language change that crosses the cross-script boundary (media-stream.ts:284). Because the charge is provider-cost-driven (session-finalizer -> billing.service.ts:90-100, markup 3.0), lost provider cost is lost margin — net ~$0.024/min of provider cost, ~$0.07/min of client charge after accounting for the offset the successor's flat estimate already covers. Cents per swap, customer under-charged never over-charged, and no production call has swapped — hence low. The genuinely larger hole is adjacent: applyTranslatorMode (media-stream.ts:250-251), applyTranslatorLanguages (:284-285) and the fallback's own `await fallback.start()` (:216) are unguarded, so if the successor throws after detach(), activeConferenceTranslators keeps the detached engine whose finalize() returns at 898 — no telephony, no finalizeSession, and the call row never reaches 'completed'. Whole call billed nothing.

**Правка.** Add a `costs` field to TranslatorCarryover carrying stt/llm/tts PLUS the leg-start timestamp, filled by detach() from costParts(). The timestamp is load-bearing, not a detail: rebase every duration-proportional estimator onto it (stealth-translator.ts:970, 974-975) so stealth bills its flat rate only for its own minutes — otherwise adding the consecutive leg's metered costs bills those minutes twice and turns an under-charge into an over-charge. Only consecutive's own account() may add inherited amounts naively, because its STT is metered off transcriber.audioSeconds. Keep telephony OUT of the carryover costs so it stays billed once whole-call from the inherited startTime (correct behaviour; finalizeSession's atomic is_finalized claim keeps it idempotent). REJECT the 'minimal alternative' of writing the leg's costs to the row and reading them back — it adds a read to the billing path and is not idempotent against the double-detach that media-stream.ts:221-225 exists to prevent. Fix the unguarded successor start in the same change: wrap it, and on failure keep a finalizable engine registered.

**Вместе с.** #18 (cancelled-stream usage) — both touch the engine/translator cost accounting; do the money pass once.

## 17. Neither utterance map is ever pruned; floor's is additionally scanned on every tick

**НИЗКАЯ** · `services/consecutive/engine.ts`

**Что ломается.** CascadeEngine.utts (engine.ts:251) has no delete anywhere — the only `delete` in the file is u.tasks.delete at 785 — so it is monotonic in distinct ids touched, and aclose() cancels entries without dropping them. Each retained Utterance keeps text, sent and said (source plus translation), a Set, a Semaphore and its own AbortController. floor.ts allocates a fresh monotonic id per turn and per candidate and live()/dropped() auto-create an entry for any unseen id, so a 4-hour call at ~3.4 turns/min accumulates 800-1500 entries, a few hundred KB to a few MB of strings that cannot be collected until hangup, on a Mac mini container sharing its memory limit with calls in progress. `context` is NOT quadratic (clamped to 3 units at 628), so this is strings, not blowup. The better lead is floor.ts:161's own `utterances` map, which has no eviction either AND is scanned with [...values()].filter(...) in ~a dozen per-tick paths (398, 438, 481, 558, 672, 696, 746, 812, 820, 943, 957, 962, 981) — same class with a real O(n)-per-tick cost.

**Правка.** Evict by a bounded id window (32 is far beyond anything the floor revisits), and clear the map in aclose() after the cancel loop (harmless, since closed = true already makes live() return null). TWO THINGS THE OBVIOUS VERSION BREAKS, both verified by reading the auto-create paths: (1) do NOT delete entries cancelled by dropped()/stopped() — live() (438-445) returns null for a cancelled entry but CREATES a fresh non-cancelled one for an unknown id, precisely so late events for a dropped utterance are not translated; deleting the tombstone means a later `updated` builds a live utterance and the engine SPEAKS text the floor dropped, which on a speakerphone is exactly what the drop existed to prevent. Keep a bounded Set<number> of cancelled ids consulted inside live(). (2) do NOT clear text/sent/said on done — floor.ts:945 can route a late tail to a released/playing utterance for up to LAG_S = 0.9s and emit 'updated'; with `sent` cleared, unsentStart() returns 0 and the whole turn is re-translated and re-emitted, so the caller hears it twice. Then add a test running a few hundred utterances and asserting the map stays bounded.

## 18. Token usage of a cancelled translation stream is never recorded, so costs.text omits work the provider billed

**НИЗКАЯ** · `services/consecutive/engine.ts`

## Почему звонки съезжали в каскад

WHY start() FELL BACK, AND WHY IT IS UNRECOVERABLE

Narrow the suspect list first. `boot()` can throw from six places, and five of them already carry a real message into the fallback event: `resolveApiKey` (credential error), `loadConsecutiveSettings`, `loadSilero` (ENOENT with the .onnx path), `openSession` (pg error), and the sibling `engine did not start` at translator.ts:307 — which is DEAD CODE, because `CascadeEngine.start()` is `async start() { return true; }` (engine.ts:270-272). That leaves exactly one branch that produces an anonymous failure: `if (!up) throw new Error('transcriber did not start')` at translator.ts:304, fed by `TranscribeLeg.start()` returning a bare `false` (transcribe.ts:123-130). So with near-certainty the 09-29 pair failed there, and the stored `reason` in the `translator_fallback` event can only ever be that constant string (media-stream.ts:210).

The leg knows the real cause and throws all of it away. Four distinct failures collapse into that one `false`, each reported only into pino: a synchronous connect throw with code/HTTP status (transcribe.ts:211); a handshake/close failure with `closeCode` (transcribe.ts:237); the 10s accept timeout (transcribe.ts:260); and an outright session refusal with the server's `error.code`/`type` — e.g. `model_not_found`, `rate_limit_exceeded` (transcribe.ts:270-271). Those need four different fixes (config, infra, network, quota) and the durable record cannot tell them apart. `lib/error-tracker.ts` is pino-only, and no session row exists yet (openSession runs at translator.ts:310, after the throw), so nothing else catches it.

MY READ ON WHICH OF THE FOUR IT ACTUALLY WAS: the two calls were 13s and 14s AND each completed one translated turn on the cascade. A 10s accept timeout would leave 3-4s for the fallback to build, connect Deepgram and finish a turn — tight. A refusal or a connect-level error fails in milliseconds and fits comfortably. So the leading candidate is the admin OpenAI key's access to gpt-live-transcribe (refusal) or a transient DNS/TLS failure to api.openai.com — precisely the two whose `error.code` / `err.code` is discarded.

THE SINGLE CHANGE THAT MAKES IT RECOVERABLE
Give `TranscribeLeg` a `lastFailure` field, set it from the same fields it already logs — inside the `fail()` closure (transcribe.ts:225, under the existing `if (ws === this.ws)` guard) and in the synchronous connect catch at transcribe.ts:210, which bypasses `fail()` — as a structured `{ kind: 'connect'|'handshake'|'refused'|'not_accepted', code?, type?, status?, closeCode?, timeoutMs? }`. Declare it OPTIONAL on `TranscriberLike` (translator.ts:59-66) so the test fakes and the smoke-scene `transcriberFactory` still compile. Then attach it at translator.ts:304 (`new Error('transcriber did not start', { cause: lastFailure })`, or interpolate), and media-stream.ts:203-214 writes the real reason into the `translator_fallback` event with no change of its own. Carry only `why()`-safe fields, never `err.message` — transcribe.test.ts:719-726 asserts the message stays out of the log because it can carry the key, and this reason now lands in durable storage.

PREREQUISITE, AND IT IS THE ACTUAL BLOCKER TODAY: that fallback event only exists in `b3e2e74`; prod runs `a4880cb` (`git rev-list --count a4880cb..HEAD` = 1). Until that commit is deployed there is no durable trace at all, so the next fallback is lost on the next redeploy regardless of the cause threading. Deploy first, then ship the cause.

## Конфликты между правками

THREE REAL CONFLICTS — resolve before writing code.

(1) #6 (shorten the first session's connect/accept budget) vs #1 (widen the reconnect recovery budget). They fight over the same two constants. `HANDSHAKE_TIMEOUT_MS` is baked into the ONE connect closure at transcribe.ts:112-113, which serves both `start()` and every mid-call `open()` from `reconnect()` (transcribe.ts:313) — so shortening it to 1.5-2s for call start also shortens every reconnect and makes #1's dead-leg outcome MORE likely on the host with documented intermittent resolver filtering. And `BACKOFF_S.length` does double duty at transcribe.ts:292 as the short-lived-session give-up threshold, so lengthening the array silently raises how many sub-10s sessions are tolerated. Resolution: in one change, (a) add a per-attempt `handshakeTimeoutMs` option and pass the short value only from `open(true)`, leaving 10s for reconnects; (b) split the give-up threshold out of `BACKOFF_S.length` into its own constant; (c) note transcribe.test.ts:477 asserts `[500,1000,2000]` literally and must change with it. Safer still: take #6 purely as an outer race in `boot()` and leave both leg timeouts alone.

(2) #10 (log drops by default) vs #11 (report a lost translation unit). Both write to the same transcript turn fields, and `untranslated` is load-bearing: it drives the CLAUDE.md silent-drop SQL and the admin health alarm (routes/admin/index.ts:221-230 -> AdminHealthBlock "Grok dropped output"). Agree the semantics once: `untranslated` means "nothing was translated" and nothing else may set it. So #11 must use a NEW optional field (`turn.partial`), not `untranslated`; #10 must keep 'no audio' on `logSkipped` (not `logTurn`, which would assert a translation the caller never heard, unmarked); and 'overlap' must stay unlogged in both (floor.ts:625-634 drops it deliberately as mis-transcription garbage, and admin/sessions/page.tsx:97 renders every entry regardless).

(3) #13 (delay `notify()` by the downstream lead) vs #3 (echo memory on pause/restart). #13 shifts `finishedAt`/`playedUntil` +400ms, which lengthens `listening()` (floor.ts:951-953) and moves the window #3's new `lastSoundedAt` predicate is measured against. Land #3 first (pure bookkeeping, no timing change), then #13/#12 together, then re-run the floor echo-window and PROMOTE_S fixtures.

ONE NON-CONFLICT WORTH PAIRING: #7 (judge threshold) and #8 (hard_end/end_silence clamp) both alter the release gate in floor.ts. Not contradictory — #8's clamp restores `hardEndS` as the last gate, which is exactly the gate #7's unsure verdicts currently fall through to — but verify them in one pass, not two.

AND ONE FIX-INTERNAL TRAP: #16's "add inherited costs in account()" must NOT be applied naively. In the consecutive->stealth direction the surviving engine is StealthTranslator, whose finalize computes STT/LLM as `durationMins * rate` off the INHERITED startTime (stealth-translator.ts:297, 970, 974-975) — adding the detached leg's metered costs on top bills those minutes twice. Carry a leg-start timestamp in the carryover and rebase stealth's duration-proportional estimators onto it, or the under-charge becomes an over-charge.
